# The Composer: an agent whose output artifact is a program.

The one thing Airflow cannot do is write its own DAGs. Considered: a headless planner inside a new `agentic-os plan` command (rejected — a second planning path outside sessions, jobs, panes, and the trace; `units.sh` remains the only headless call, for wave decomposition); an in-repo TypeScript agent loop with its own tool-calling (rejected — the OS is a supervisor around host agent CLIs, and a hand-rolled loop under `src/` duplicates every worker pane while dodging admission, layout, and the retry cap). Adopted: the main-agent entry is dogfood — a meta-program, the **Composer**, whose own dag is `actor → gate`: its Actor takes a task (`task.txt` for a cold start from nothing, or one bound to a project via `roots.txt` + a minted `project.json`), studies the example programs and the rails contract, and writes a new `agentic-program/<name>/` folder — `dag.mjs`, `workflow.toml`, `hooks/`, `actor.md`, `task.txt`; a `gate` step holds for human approval, honoring RAILS ("a planner may write hooks; it may never rewrite rails"); the existing run door then books the new program like any other, with validator-in-the-loop ground truth (`assertProgram`, `loadManifest`) as the Actor's environment feedback. The plan is plan-and-execute taken literally: the plan is a durable, versioned, diff-able file; the agent is used once at compile time, the workflow many times at run time. Milestones: M1 CLI — `agentic-os run` on the Composer program, zero new surface code; M2 `POST /api/plan` in the web window; M3 a chat entry in the window. Landing it adds a Composer entry to CONTEXT.md. (Proposed in the jd-research lane; coworker and ui-window have merged, so the implementation spawns off master.)

# Zen 1 — decision log

Verbatim record of the user's discussion with another agent, 2026-09-29.
This is the trail, not the marketing. Early answers were overwritten. Only the **Final** lines are law. The rest is why those lines exist.

## What we were trying to protect

A previous tool (`stand_up`) was advisory. A model decided a task was "too trivial to route." At that moment there was no system, only a chat with opinions. Zen 1 exists so spawn cannot be a habit.

---

## Q. What kind of product is this?

**Tried:** "An OS like the kernel / like K8s admission — the only way programs run."

**Rejected because:** First Mate already runs, talks, and can edit before any rail. That is a shell, not Linux. `cd`/`ls` on a real OS already go through the kernel; our waiting-room chat does not.

**Final:** A **shell + supervisor**. "OS" is a nickname for process birth, accounting, isolation — not "nothing runs until we say so."

---

## Q. What is the one gate?

**Tried:** Every prompt is a task. Then: the gate is "enter the rail" after a plan, human types enter. Then: two ceremonies (human enter + JEV).

**Rejected because:** "Every prompt" makes "ok" a process. "Gate = execute only" puts planning and tools back in lawless chat (the `stand_up` bug). Two birth canals means two places to skip.

**Final:** **JEV is the only birth canal for workers (panes).** Talking is not a birth.

---

## Q. What is a task / process / worker?

**Tried:** Any single prompt.

**Rejected because:** Explodes into process-per-utterance, and contradicted "nothing is a task until the rail."

**Final:** A **pane** (subagent process) is the worker. A **Job** is the process group those panes belong to. A **session** is the conversation + worktree First Mate can switch onto.

---

## Q. Can work exist before the OS?

**Tried (A):** Chat is outside the OS; OS begins at promote-to-Job. IDs only at execute.

**Tried later:** First Mate is fully a coding agent before the rail; OS "takes over" after.

**Then regretted:** Wanted grill/summary panes from First Mate, so First Mate must be *in* the product, with an OS toolbox.

**Final split:**

- **Session** — always in the product. Always has `session_id` + worktree + log. May have **no Job**. Talk + disposable tree. Reap later.
- **Job** — only when managed work starts.
- **Pane** — only at JEV, and JEV requires a Job.

Jobless session: **no JEV**. First pane request is admission: create Job on this session, then JEV.

---

## Q. Who may admit a pane?

**Tried:** Model routes when it feels like it (`stand_up`). Human "enter the rail" as the whole OS.

**Final:** **Model proposes, policy admits.** That pair *is* JEV. Human does not have to type "enter" for every pane; policy can still require a human for some classes of spawn. Triviality is not an exemption.

---

## Q. One First Mate or many?

**Tried:** Hybrid session/job objects. Then: First Mate stays a coder *and* OS starts panes (two writers). Then: 10 parallel Jobs from one First Mate.

**Final:** **One First Mate process (the shell). Many Jobs.** First Mate is not pane 0 unless you later decide that explicitly (we did not). It can *ask* for panes; it is not itself a JEV child.

---

## Q. Session vs Job vs pane?

**Final cardinality:** Normally **1 session : 1 Job : N panes**.

- Job = managed group (id, budget, policy, state).
- Session = log + worktree First Mate switches to. May exist with Job = none.
- Pane = child process, `parent = Job`, born at JEV.

Pane turns are **in the pane**. They are not a second First Mate.

---

## Q. Where does the user answer a pane?

**Tried:** Wake First Mate, push session stack, handle message, pop — "for that message only."

**Rejected as tty-claim for Q&A because:** If you pop before the human replies, "yes, deploy" lands in the wrong session.

**Final:** **Option 1 — pane is a separate room.** User talks to the subagent **in the pane**. First Mate may receive a one-line wake (FYI / "look at pane P") and immediately return to the current user session. Official answers are not taken in First Mate.

---

## Q. Worktree?

**Tried:** New worktree before every edit.

**Rejected because:** One tree per save.

**Final:** **One worktree per session.** Normally one session per Job, so also one tree per Job. New talk defaults however you already do (e.g. from master) unless the user points at an existing session tree. Panes of a Job share that Job's session tree unless a later zen isolates them.

---

## Q. What must not exist without JEV?

**Tried:** No id, no tools, no spawn (whole First Mate locked down). Then: no id until execute.

**Final (narrow):** Without JEV there is **no pane**: no child id, no child budget, no child process. First Mate and a jobless session may still exist. They must not self-spawn workers.

---

## Why the zen is two files

`zen.core` is the invariant another agent can refuse to violate.
`zen.decision` is how *this* product interprets it (shell vs child, session without Job, who talks where). Those can change without throwing away the gate.

**zen.core**

> Every worker is born at JEV.
> A session can exist without a Job. A pane cannot.
> No JEV, no pane.

**zen.decision**

> First Mate is the shell, not a child.
> A session always has an id and a worktree.
> The first admitted spawn on a session creates the Job, then the pane.
> JEV: model proposes, policy admits.
> User talks to a pane in the pane. First Mate may get a wake; it does not take the answer.

---

## Do not resurrect

- Every prompt is a process
- Gate = "after plan, at execute" as the only door
- Advisory routing / "too trivial to spawn"
- Two writers on the same tree (First Mate coding *and* panes) without a later isolation zen
- Taking pane yes/no in First Mate while also instant-popping the session

If a future change needs one of those, it is a new zen, not a silent edit to zen 1.

# Decision log — zens 1–5

Verbatim record, 2026-09-29. Early answers were overwritten. **Final** lines are law. The rest is why.

## Zen 1 — one gate

**Tried:** Every prompt is a task. Chat is outside the OS. Gate = "enter the rail" after plan. IDs only at execute. First Mate is a full coding agent until takeover.

**Rejected:** Prompt-as-process explodes. Execute-only gate makes routing advisory again (`stand_up`). "Outside the OS" blocked grill/summary panes. Kernel/K8s poetry oversold what this is.

**Final:** Shell + supervisor, not Linux. **JEV is the only birth canal for workers.** Session may exist with no Job. First pane request creates the Job, then the pane. Model proposes, policy admits. User talks to a pane **in the pane**. First Mate may get a wake; it does not take the official answer.

**zen.core**
Every worker is born at JEV.
A session can exist without a Job. A pane cannot.
No JEV, no pane.

**zen.decision**
First Mate is the shell, not a child.
A session always has an id.
The first admitted spawn on a session creates the Job, then the pane.
JEV: model proposes, policy admits.
User talks to a pane in the pane. First Mate may get a wake; it does not take the answer.

## Zen 2 — disposable workers, durable state

### Q. What is "the agent"?
**Tried:** All agents, including the thing you talk to.
**Final:** **Panes** (and a relaunchable orchestrator). First Mate is the shell and is **not** disposable.

### Q. What is "RAM"?
**Tried:** "Panes are RAM."
**Rejected:** Collides with zen 1 (panes are **processes**).
**Final:** Pane = process. Its **context window** is scratch. Rule 2 is about where *state* lives, not what a pane *is*.

### Q. What outlives the pane?
**Tried:** Task directory from the blog. Then `sessions/<sid>/` containing a worktree. Then worktree-as-OS-storage.
**Final split:**
- **OS disk** = `sessions/<sid>/` (trace, `state.json`, ledger, pane records).
- **Project bytes** = git worktree **in the target repo**.
- Session stores a **binding** (`repo`, `worktree_path` / ref), not a copy of the tree.

### Q. Resume after days / "fix job 1"?
**Final:** Session + binding + worktree stay. Job record stays on disk (`retired` is a state, not `rm`). Reopen = same session, new JEV, same tree. Merge to master is a different command.

**zen.core**
Workers are disposable processes.
Durable state lives outside them.
If the work exists only in a worker's head, you cannot kill it, resume it, or run another one.

**zen.decision**
Workers = panes (and a relaunchable orchestrator). First Mate is not a worker.
Durable OS state = `sessions/<sid>/`.
Project bytes = bound worktree in the target repo.
A pane's context window is scratch; it must write what the next pane needs.

## Zen 3 — rails vs hooks

**Tried:** Inventory rails/hooks now (JEV, tty, reaper, stage graph, grade, …).
**Final:** **Deferred** until the system has been used. Core kept; list not invented from the fleet blog.

**zen.core**
Rails do not change per Job. Hooks do.
A planner may write hooks. It may not rewrite rails.

**zen.decision**
*Deferred.*

## Zen 4 — wakes and attention

**Tried:** Failures wake, successes stay silent — globally. Grill/summary must not ping First Mate.
**Rejected as global:** Grill/summary exist *for* First Mate; they should report done. Silence was about **orchestrator + fan-out**, and about not burning orchestrator tokens, not about muting the shell.

**Final:** Two parents, two budgets. Abstract core; orchestrator rule lives in decision.

| Parent | Children | Wake |
|---|---|---|
| First Mate | grill, summary, other direct panes | May report to FM, including done |
| Orchestrator | fan-out workers | Success is not an event; failure/stuck wake the orchestrator |
| Job-final | — | May wake First Mate once |

JEV should stamp `parent: first_mate | orchestrator` or the two rules get mixed.

**zen.core**
Attention is a budget.
A quiet success is not an event.
A wake must mean something.

**zen.decision**
First Mate direct panes may report to First Mate, including done.
Orchestrator fan-out does not wake the orchestrator on success. Failures and stuck do.
Job-final may wake First Mate once.

## Zen 5 — receipt

**Tried:** Retired-to-zero = everything gone (panes, Job, tree, session).
**Rejected:** Blocks reopen and "keep this worktree, don't merge."
**Final:** Receipt = **panes of this Job → 0**. Session, worktree binding, and Job record remain.

**zen.core**
A Job is not finished when the last pane thinks it is finished.
It is finished when the receipt says panes remaining = 0.

**zen.decision**
Receipt = pane count for that Job.
Session, worktree, and Job record remain so you can reopen on the same tree.
Deleting a worktree or merging to master is not retire; it is a separate command.

## Do not resurrect

- Every prompt is a process
- Gate = execute-after-plan only
- Advisory spawn / "too trivial"
- "Panes are RAM" as the definition of a pane
- OS owns a copy of the repo
- One silence rule for both First Mate and orchestrator
- Retire = delete the tree
- Taking pane yes/no in First Mate while instant-popping the session

Zen 3's hook/rail inventory is the open hole. Fill it from use, not from the blog's nouns.
